### SL-3a transaction and record contract

The total nested acquisition order is **lease → generation operation → reservation journal → launch request**. A transaction may start at any level and omit levels. Release each lock before acquiring an earlier one. In particular fence_launch returns with its operation lock released, including on timeout. No cancel client holds the operation or journal lock across a socket exchange. The supervisor holds the lease while serving the attempt. Its initial journal transaction begins at provisioning and ends at claim.

SL-3a provides these additional methods in sandbox_placement.py. In these signatures `K` expands, in order, to `reservation_id: str, request_id: str, generation: str`. PreparedPaths and LaunchRequest come from launch_process_contract.py, and ReservationLock is the landed sandbox_placement.py lock. The generation is a fresh 32-character lowercase hex nonce per election. SL-3a owns the following immutable data shapes: Owner = {pid: positive int, start: nonempty process-start identity string}; FileId = (device: int, inode: int); AllocationKind = stage or scratch; Debt = the cleanup-debt fields in the table below. All paths derive from trusted roots and validated IDs. Deadlines bound waits and I/O. Success requires durable publication or confirmed collection.

SL-3a's client connects to the SL-8 supervisor's named AF_UNIX stream at `<client-launch-root>/ctl/<generation>.sock` (0700 directory, 0600 socket). Open the private root without symlink traversal. Publish the listener before claim and remove only the owned inode at teardown. A bind/connect error fails closed. Both ends obtain SO_PEERCRED before reading application data. The client matches server uid, pid **and current start identity** to the recorded supervisor; the server requires its service uid and matches peer pid and observed start identity to sender_pid and sender_start in the frame. Revalidate the claim and generation before acting. Unsupported peer credentials or a stale start identity give owner_unverified. The client uses one request and one reply per connection, both 4-byte unsigned big-endian length followed by strict UTF-8 JSON, max 4096 bytes each, within one deadline. Reject unknown keys, duplicate keys, surplus frames and mismatches. Request keys are version=1, op="cancel", reservation_id, request_id, generation, sender_pid and sender_start. Reply keys are version=1, generation and outcome, with the landed CancelOutcome literals (cancelled, already_terminal, cancel_pending, unknown_attempt, owner_unverified, owner_not_live). An acknowledgement of intent alone gives cancel_pending. A malformed, late or unverifiable exchange never establishes successful cancellation. The server takes the operation lock to serialize cancellation with start and publication. The startup/verdict socketpair cannot authorize this operation.

**Record protocol.** Before admission serialize by client/request ID, hash the complete canonical launch body, compare any existing digest, return a matching stored terminal verbatim, and reject a different body without touching the record. Elect one caller by exclusively creating an in-flight record with verified process/start identity and a fresh generation. Release the record lock before expensive work. A same-body duplicate attaches and waits in bounded observations, checking cancellation and the durable terminal, never spawning another helper or taking ownership from a live original. Bound recovery checks by ANSWER_BOUND_S per call. A verifiably dead pre-claim owner with confirmed no claim and no handoff settles a generic pre-claim refusal. When liveness cannot be established, an ambiguous handoff or missing terminal after claim reports wire-valid uncertain on bounded observation, preserves the generation and claim, and leaves reconciliation to reap. A transient uncertain observation is never stored over the original terminal. Use one compare-and-set under the short request lock for every launch-request record transition, including terminal; bind it to the owner and generation. Hand off once to an identified supervisor which acknowledges ownership durably before caller ownership ends. Crossing caller exit after that acknowledgement leaves the attempt running.

**Allocation and claim.** Each elected request journals a private stage beneath trusted client storage, outside any prepare run a concurrent release can remove. Record reservation, request, run, generation, owner and exclusive stage name before creation. Only matched dead-owner stages are collectible. Different IDs may stage concurrently. The supervisor takes the lease and then the reservation journal lock, rechecks window, prepare, expiry and claim, and checks its own start identity before provisioning. A held winning claim refuses a contender as exec_claimed even while the winner holds the lease (read claim under a short bounded transaction if the lease is busy). Record intent for a generation-named scratch allocation before exclusive creation. Provision there, record its device/inode, fsync and rename without replacement to the prepared path under the same lock; recover from either side of rename by matching identity and intent. Unknown or foreign ownership leaves debt. Call lock.return_dir(run_id) under that lock to provision the retained parent in returns/ outside runs/. Pass its result to collection. Finish with lock.claim(request_id, run_id, generation=generation, owner=verified_identity) and release the journal lock immediately. Missing identity returns capability_unmet with zero starts and no rollback record. The supervisor holds the lease through durable terminal publication. Failure paths remove only their own staged allocations. A pre-claim crash leaves a recoverable intent, never authority to clear a claim.

**Post-claim interlock.** Serialize start authorization, return publication, generation fence and cancel with a distinct per-generation operation lock. The supervisor validates the unfenced generation and durably marks start-intent before entering the bounded spawn under that lock. An uncertain start keeps the claim. Release/reap obtain the journal lock only to snapshot ownership, then drop it before atomically recording release intent with the operation fence, signalling, waiting for terminal, or acquiring the lease. No path waits for the lease or operation lock while holding the journal lock. Only after acquiring the lease and rechecking generation, terminal (or a verified dead-owner disposition) and cleanup evidence under the journal lock may teardown proceed. A timeout at any stage yields cleanup_pending. Treat unbounded spawn or blocked I/O as unresolved debt with activation gated on bounded containment. Terminal metadata remains publishable while fenced. A durable fence blocks any later chain start or retained byte publication.

For a closed rollback cause the live supervisor retains the lease, obtains a fresh journal lock for at most the remaining release allowance, and calls lock.rollback(request_id, generation=generation) only with proven zero starts, matching claim and the closed-cause evidence. Persist cause/intent before CAS and finish the request terminal before releasing the lease. A rollback marker proves a completed CAS across crash recovery; an intent alone never does. A timeout, unknown remote effect or unconfirmed CAS keeps the claim uncertain. Reap scans fenced/debt records and claims with verified gone owners even before expiry. Record fencing and debt before teardown, and keep the allocation until descendant exit and parent collection (remote expiry/barrier on OpenShell) are independently confirmed. Never manufacture acknowledgement, a completed cancellation, or rollback on restart. Retained returns survive ordinary release/reap until tombstone expiry.
